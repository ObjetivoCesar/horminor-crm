## 2. Autenticación de servicio

No es login de usuario. El servidor resuelve el rol y nunca confía en el rol
del JSON.

| Header | Uso |
|---|---|
| `X-Actor-Token` | Token de servicio. Se compara con `CUSTODIO_TOKEN_SUPERADMIN`, `CUSTODIO_TOKEN_CONTADORA`, `CUSTODIO_TOKEN_SECRETARIA`, `CUSTODIO_TOKEN_BODEGA`, `CUSTODIO_TOKEN_CHOFER` o `CUSTODIO_TOKEN_SYSTEM_CRON`. |
| `X-Actor-Id` | Identificador nominal. Si falta: `{ROL}_DEFAULT`. |
| `X-Channel` | `WEB_PANEL` (default), `WHATSAPP`, `SYSTEM_CRON`, `TEST`. |
| `X-Actor-Role` | Solo si `CUSTODIO_ALLOW_DEV_HEADER=true` y no hay tokens configurados. |

Reglas:

- Si no hay tokens configurados y `CUSTODIO_ALLOW_DEV_HEADER=false` → `503 GATE_AUTH_NOT_CONFIGURED`.
- Token inválido → `401 UNAUTHORIZED_ACTOR`.
- `SYSTEM_CRON` solo por `SYSTEM_CRON`; y viceversa.
- `X-Gate-Key`/`Authorization: Bearer` se conserva como compatibilidad legacy.

## 3. `POST /api/v1/secretaria/pagos`

Ventanilla única para `COBRO`, `GASTO_CAJA_CHICA` y `GASTO_BANCARIO`.

```json
{
  "request_id": "uuid-opcional",
  "tipo_movimiento": "COBRO",
  "cliente_id": "uuid",
  "order_id": null,
  "fecha": "2026-11-09",
  "metodo": "EFECTIVO",
  "bolsa": "CAJA_DIARIA",
  "monto": "500.00",
  "es_anticipo": false,
  "account_slug": null,
  "referencia": "REC-0012",
  "descripcion": null
}
```

- `request_id` es opcional; si no viene, el servidor genera uno y lo devuelve.
  Para reintentos seguros, el cliente debe reenviar el mismo `request_id` o el
  header `Idempotency-Key`.
- `COBRO`: `cliente_id` obligatorio; `order_id` opcional. Se traduce a
  `REGISTER_CLIENT_PAYMENT`.
- `GASTO_CAJA_CHICA` / `GASTO_BANCARIO`: `account_slug` y `descripcion`
  obligatorios; se traduce a `REGISTER_EXPENSE`.
- `monto`: decimal positivo, máximo 2 decimales.
- `metodo`: `EFECTIVO` o `TRANSFERENCIA`; la bolsa se deriva si se omite.
- Un reintento idéntico devuelve `200` con la misma respuesta; un payload
  distinto con el mismo `request_id` devuelve `409 PAYLOAD_HASH_MISMATCH_ON_RETRY`.

### Respuesta

`201 Created` con el sobre del Gate:

```json
{
  "contract_version": "1.3.0",
  "request_id": "uuid",
  "status": "ACCEPT",
  "rejection_codes": [],
  "residual_risks": [],
  "witness_id": null,
  "transaction_group_id": "uuid",
  "approval_request_id": null,
  "data": {
    "payment_id": "uuid",
    "monto": 500.0,
    "parte_cxc": 500.0,
    "parte_anticipo": 0.0,
    "saldo_pendiente": 0.0,
    "saldo_a_favor": 0.0
  }
}
```

### Códigos HTTP

| Situación | HTTP | Código |
|---|---|---|
| Aceptado | `201` | `ACCEPT` |
| Reintento idéntico | `200` | `ACCEPT` |
| Pendiente de Julio | `202` | `PENDING_JULIO_APPROVAL` |
| Sin auth configurada | `503` | `GATE_AUTH_NOT_CONFIGURED` |
| Token/actor inválido | `401` | `UNAUTHORIZED_ACTOR` |
| Rol sin permiso | `403` | `UNAUTHORIZED_DOMAIN_ACCESS` |
| Contrato/saldo/comprobante | `422` | `SCHEMA_VALIDATION_FAILED`, `PAYMENT_EXCEEDS_PENDING_BALANCE`, `MISSING_VOUCHER_REFERENCE`, `BOLSA_METHOD_MISMATCH` |
| Idempotencia distinta | `409` | `PAYLOAD_HASH_MISMATCH_ON_RETRY` |

## 5. Reembolso al aprobar una anulación

`RESOLVE_APPROVAL_REQUEST` acepta `modo_resolucion_cobro`:

- `CONVERTIR_A_ANTICIPO_CLIENTE`: reclasifica los cobros de `1103` a `2102`;
  el cliente conserva `saldo_a_favor`.
- `DEVOLVER_DINERO_CAJA_O_BANCO`: inserta `REEMBOLSO_CAJA` por cada cobro,
  revierte contra la bolsa original y marca el cobro original como borrado
  lógico.

Si la orden tiene cobros y el modo falta, la aprobación no se marca
`APPROVED`: se rechaza con `SCHEMA_VALIDATION_FAILED` y la solicitud sigue
`PENDING`.
